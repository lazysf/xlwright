# 設計

本書は [要件](requirements.md) を満たすための現行設計です。
実装・実機検証の完了を意味しません。
実機に依存する仮説は [Spike-0](spike-0.md) で検証します。

## 構成

C#/.NET 10とMicrosoft Office Interopの直接利用を採用します。
MCPサーバー内に専用STAスレッドを1本置き、専用Excelを起動・管理する単一プロセス構成を検証します。

```text
Codex / Claude Code
  └─ MCP（stdio）
      └─ XlWright.McpServer
          └─ XlWright.Core（MCP非依存）
              └─ 専用STAスレッド
                  └─ 専用EXCEL.EXE
```

ExcelはCOMの外部プロセスです。MCPサーバーの子プロセスとは仮定しません。
COMオブジェクトの生成・操作・解放は専用STAスレッドに集約します。
Windowsメッセージポンプを維持し、COMオブジェクトをスレッド外に渡しません。

状態照会はCOMを使わず、サーバーの保持情報から応答します。
専用STAが塞がっていても状態照会が応答することをPoC-1で検査します。

MCP接続基盤はR1の環境整備で前倒しします。[採用判断](adr/0002-development-mcp-foundation.md)に従い、開発用機能を製品の通常起動から分離します。SDKの取得・依存確認の状態は[環境記録](notes/verification-environment.md#mcp接続基盤の依存確認)を参照してください。
独自プロトコル実装、汎用キュー、復旧用の別プロセスを先行して追加しません。

## ブックとソース

利用プロジェクトのルートに `project.yaml` を置きます。
相対パスは設定ファイルのあるディレクトリを基準に解決し、セッション中は固定します。

| `paths` のキー | 内容 | 既定値 |
| --- | --- | --- |
| `workbook` | 主ブック。必須 | なし |
| `vba_source` | VBAソースの正本 | `src` |
| `tests` | テスト資産 | `tests` |
| `workspace` | 実行時の一時領域 | `.xlwright` |
| `dist` | 成果物の出力先 | `dist` |

認める設定はこの5項目だけです。不明なキーは拒否します。
主ブックの拡張子は `.xlsx` または `.xlsm` とします。
`.xlsx` ではVBA反映とマクロ実行を拒否します。
開始時にはブック、VBAソースディレクトリ、テストディレクトリが存在することを要求します。
読取専用でしか開けないブックでは開始しません。
`workspace` と `dist` が原本ブック・ソース・テスト資産と重なる場合は、リンク経由も含め拒否します。
プロジェクト外のパスを一律に禁止する設計ではありません。

VBAはソースから一方向に反映し、初回取り込み時だけExcelから抽出します。
VBEでの直接編集は通常フローに含めず、変更を検出しません。
ソースファイルが存在しないことだけを理由に、既存モジュールを削除しません。
保存とGit commitは独立した操作です。

## 実行制御

公開セッション状態は `closed`・`ready`・`isolated` です。
実行中であることは `busy` で表します。
開始・終了処理中は内部の遷移とし、公開状態としては永続化しません。復旧判断に必要な起動印と所有記録は、後述の形式で永続化します。

STAの実行枠は1件です。競合する要求を待機させず即時拒否します。
マクロとテストは非同期ジョブとし、同時に1件だけ実行します。
実行中は状態照会を受け付け、編集・保存・別実行・終了を拒否します。
P0には実行中マクロの強制キャンセルAPIを設けません。

| 操作 | 既定タイムアウト |
| --- | --- |
| セル等の同期COM操作 | 30秒 |
| セッション開始・保存・終了 | 各120秒 |
| マクロ・テスト | 600秒。呼出しで1〜1800秒を指定可能 |

経過時間は単調時計で計測します。
タイムアウトは処理の停止を証明しません。結果不明なら `isolated` にし、以後のExcel操作と保存を拒否します。
遅延完了は診断として回収し、通常の操作列や保存・Close等の次段を再開しません。
遅延した成功だけで `ready` へ戻しません。競合時の確定順序は初期ライフサイクル契約、応答はAPIに従います。
Excelの呼出し拒否 `SERVERCALL_RETRYLATER` だけを、操作のタイムアウト内かつ合計最大10秒まで再試行します。
受理された呼出しの失敗・無応答・切断は再試行しません。再試行方式はS9で検証します。

## 終了と残存Excelの後始末

プロジェクトルートの `.xlwright.lock` を `FileShare.None` で保持します。
ロックファイルは、ExcelのPID・生成時刻・主ブックのパス等の所有記録も兼ねます。
サーバー終了でOSのロックが外れても、残存Excelの所有記録を次回開始時に確認します。
所有記録の必須項目が欠ける場合は `SESSION_RECORD_INVALID` で開始を拒否します。

R1〜R5では、残存Excelがある場合や終了を確認できない場合は、後述の手動復旧へ進みます。
残存Excelへの自動COM接続・終了、`force`、保留中呼出しのある `isolated` からの制御用破棄終了は、後続の設計対象として残します。
以下の当該経路は初期PoCの必須実装ではありません。未対応要求の拒否応答はAPIの初期ライフサイクル契約に従います。

終了安全確認は、通常終了、破棄終了、サーバー終了時、次回開始時の残存Excelの後始末に適用します。

1. 記録されたPID・生成時刻・プロセス名を照合します。同一性が一致しなければ終了しません。
2. COMが応答する場合、開いているブックの `FullName` がすべて主ブックまたは管理対象のテストコピーであることを確認します。
3. COMが応答しない場合や、管理対象外のブックがある場合は終了せず、`EXCEL_NEEDS_REVIEW` と診断を返します。
4. `force: true` は、対象と未保存内容を失う可能性を人に示し、明示的承認を得た後だけ使用します。同一性確認と所有記録の形式検証は省略しません。

現在のセッションには専用STAから照会します。
残存Excelは、記録されたプロセスのウィンドウからApplicationを取得し、`Hwnd` のPIDも照合します。
残存Excelへの照会には時間制限を設けます。ウィンドウの表示状態を終了許可の根拠にはしません。

通常終了は、主ブックの保存成功を確認してから終了安全確認へ進みます。
保存の失敗が明確なら `ready` とロックを維持します。成否不明なら `isolated` とします。
終了確認後に所有記録をクリアしてロックを解放します。
`session_end` の `force` は `discard: true` の場合だけ有効です。
破棄終了は保存せずに行いますが、終了安全確認は省略しません。

サーバーのEOF・終了要求では保存せず、終了安全確認を満たすExcelだけを終了する方針です。
確認できなければExcelを残します。
この場合も、後述の初期ライフサイクル契約に従って所有記録を保持・クリアします。

COMの保留中呼出しがある場合は、新しいSTA操作を開始しません。
同一サーバー内復旧の設計では、所有Excelの終了後、保留中呼出しが戻るまで既定30秒待ちます。
戻らなければ `STA_UNRECOVERABLE` とし、サーバー再起動を要求します。STAを作り直して継続しません。
この復旧経路はR6でS12を実施して採用可否を評価します。PoC-1では回収成功や `STA_UNRECOVERABLE` の不発生を要求しません。
PoC-1で状態照会、隔離、後続処理の抑止、手動復旧が成立しない場合は、原因を切り分けて代替構成を比較します。
実装不良と構成上の制約を区別する手順は [PoC-1の評価](spike-0.md#poc-1の範囲と合格条件) に従います。

### 初期の手動復旧

「安全に停止」は新しい自動操作を止めた状態です。実行中のVBAやCOMの停止を意味しません。
所有確認・排他・所有記録・隔離・遅延処理の抑止・状態照会は初期から必要です。
異常時は次の順に人へ引き継ぎます。

1. 対象ブック、記録されたプロセスの同一性、失敗段階、結果不明の操作、残存の可能性を診断で確認します。所有を証明できない場合は推測で終了対象を選びません。
2. 自動操作を停止し、旧サーバープロセスの終了を確認します。以後そのサーバーの遅延処理が動かないことを確認してから、人のExcel操作へ移ります。Excel側の処理が止まったとはみなしません。
3. 人が対象Excelと未保存内容を確認し、変更を保存するか破棄するかを決めます。確認できない場合は復旧を保留します。
4. 人が確認した対象を終了し、対象プロセスが終了したことを確認します。他のExcelを一括終了しません。
5. 診断と終了確認の根拠を残し、所有記録を整理します。記録を削除するだけで再試行しません。記録不正やPID不明の場合も、残存可能性を解消できなければ保持して開始を拒否します。
6. 新しいサーバーで、排他と記録の検証を経て開始します。旧セッションの処理結果を引き継いで成功扱いにしません。

記録の整理は、旧サーバーと対象Excelの終了を確認し、診断と確認根拠を残してから、下記の完了記録に置き換える操作です。作業中は他のサーバーを開始しません。削除だけで開始制限を解除しません。所有不明・残存可能性を解消できなければ整理を保留します。

### 初期ライフサイクル契約（R1〜R5）

T2で採用した設計契約です。この契約を使う[初回コンソール](notes/spike-0-preparation.md)と[実機の確認範囲](notes/spike-0-results.md)を記録しています。製品のライフサイクルAPIは未実装です。採用理由は[ADR](adr/0001-initial-lifecycle.md)に記載します。
以下は初期経路の規定であり、前節の後続経路より優先します。
公開の破棄終了、force、残存Excelへの自動COM接続・終了、隔離中の制御用終了は提供しません。
EOFの安全確認付き後始末は公開の破棄終了とは別に扱います。

#### 所有記録の形式

`.xlwright.lock` はUTF-8のJSONオブジェクトとします。書込み時はBOMを付けません。

| `kind` | 必須フィールドと意味 |
| --- | --- |
| `starting` | `version: 1`, `kind`, `workbook_path`。Excel生成前の起動印 |
| `owned` | 上記に加え `process: { pid, started_at_utc, name }`。所有同一性の確定記録 |
| `completed` | `version: 1`, `kind` のみ。所有中のプロセス情報を残さない完了記録 |

`workbook_path` は開始時に正規化した主ブックの絶対パスです。
`pid` は正の整数、`started_at_utc` はUTCのISO 8601日時（.NETのラウンドトリップ形式）、`name` は照合対象のプロセス名です。
所有記録は実行時情報であり、実際の個人パスを仕様例や結果文書へ転記しません。
新規作成に成功したファイルだけを初回と判定します。存在確認だけで初回とはみなしません。
既存の空ファイル、壊れたJSON、未知の版・種別、必須情報の欠落・型不正は開始拒否です。
読取り失敗を形式不正やプロセス不在に置き換えません。

排他取得前に既存ファイルを切り詰めません。
更新は保持中の同じハンドルで、書込み、ファイル長の確定、`FileStream.Flush(true)`、読戻しと内容照合の順に行います。
確認が完了するまで次のExcel操作へ進みません。通常の状態やbusyの変化では記録を書き換えません。
この手順は原子的更新や電源断後の追跡保持を保証しません。更新途中の停止で所有情報が欠けた場合は手動復旧へ渡します。

#### 遷移と失敗境界

| 経路 | 処理順と成功条件 | 失敗時の状態・保持 |
| --- | --- | --- |
| 起動 | 設定検証 → 排他取得 → 既存記録確認 → starting書込み・確認 → Excel生成 → 同一性取得 → owned書込み・確認 → 起動設定・Open → ready | 生成前の失敗はclosedで、自分のロックを解放。生成着手後の失敗はisolatedで記録とロックを保持。owned確認前はOpenしない |
| 通常終了 | 保存成功 → 終了安全確認 → 保存しないClose・Quit → 対象プロセス終了と保留処理終息の確認 → completed書込み・確認 → ロック解放 → closed | 明確な保存失敗はready。保存結果不明、部分終了、終了未確認、完了記録更新失敗はisolated。記録とロックを保持し、自動再送しない |
| 安全確認による拒否 | 同一性と全ブックを照合し、ProtectedViewWindows.Countが0と確認できた場合だけ終了へ進む | 元がreadyで管理外ブック・Protected Viewの存在が確定し、同一性も確認できる場合はreadyを維持。元がisolatedならisolatedを維持。同一性不一致・確認不能・結果不明はisolated。記録とロックを保持 |
| EOF・サーバー終了要求 | 保存せず、保留中COM呼出しがない場合だけ安全確認付き後始末を試みる | 保留中なら追加STA操作を投入しない。確認不能・期限内未完了なら記録を残す。forceしない。サーバー終了時のOSロック解放は記録クリアの証拠ではない |
| 次回開始 | 新規作成または検証できるcompletedから起動へ進む。ownedのPIDがOS照会で確実に不在ならcompleted更新・確認後に進む | starting・不正記録・残存・同一性不一致・照会失敗はclosedで拒否。記録を変更せず、自分のロックを解放。残存へCOM接続・終了しない |

Quitの成功やCOM参照解放だけをプロセス終了の証拠にはしません。
起動失敗後も自動破棄終了へ進まず、手動復旧へ引き継ぎます。
保存失敗からの公開破棄終了も初期は提供しません。
EOFも開始・保存・終了の既定120秒を超えて通常列を継続しません。期限到達は呼出しの停止を意味しません。
旧サーバーが終了したことを人が確認するまでは、人によるExcel操作へ移りません。

#### 期限と完了の確定

期限判定、完了の受理、次段の実行許可を同じ制御下で決め、応答を一度だけ確定します。
開始前に期限切れなら呼出しを投入しません。開始済みの呼出しは停止したとみなしません。
期限切れ後は次段への許可を失効させ、遅延結果・例外は診断として回収するだけとします。
Openの遅延成功でreadyにせず、保存の遅延成功でCloseへ進みません。
通常列の継続がないことを確認するまでbusyを維持します。回収後もisolatedを維持します。
旧処理が新しいセッションの状態や所有記録を書き換えることを許しません。
応答と拒否の対応は[初期API契約](api.md#初期ライフサイクルの提供範囲)に従います。

## 起動とコード実行の境界

専用Excelは既定で `Visible=False` とします。
`XLWRIGHT_EXCEL_VISIBLE=1` のときだけ可視化し、専用ウィンドウであることをCaptionに表示します。
非表示を、終了して安全である根拠には使いません。

開発ブックとテストコピーは信頼済みコードとして `AutomationSecurity=Low` で開く設計です。
外部ブックを取り込む `project_init` では、コピーを事前にOOXMLとして確認し、XLMマクロシートを拒否します。
取り込み時は `ForceDisable` で開いて抽出し、保存せず終了します。
抽出したVBAは、通常のセッションを開始する前に人またはエージェントが確認します。
既知のVBAフィクスチャによるLow・イベント抑止・ForceDisableの起動比較は、[T7の評価](notes/spike-0-results.md#t7の評価と残る確認)に記録しています。
ForceDisableによるVBA抽出は未実施で、`project_init`の実装前に確認します。ActiveXは非対応です。

xlwright自身のOpen・Close・編集はイベント抑止の下で行い、終了後に元へ戻します。
イベント抑止は、VBA全体の実行防止を保証するものとして扱いません。
`DisplayAlerts=False` はシート削除や保存しないClose等の明示操作中だけに限定します。
マクロやテストの実行中は変更しません。

同一ユーザー権限で動くVBAは、ユーザーの個人ファイルにもアクセスできます。
ブック外のファイル操作は `paths.workspace` 配下とテストデータに限る運用です。
ファイル削除やネットワークアクセスを含むVBAは、実行前に人へ報告します。
xlwrightによる技術的な強制は保証しません。
保護されたVBAや組織の信頼設定は変更・迂回しません。

COM照合では、主ブック自体への人の未保存編集や、照合直後に別ブックが開かれる可能性まで排除できません。
`force` の人の承認は運用規約であり、MCPツールだけで承認者を認証できるとは扱いません。

## テストと診断

テストはソース反映 → 開発ブック保存 → イベント抑止でClose → 一意な同名コピー作成 → コピーで実行 → 結果保存 → 保存せずClose・削除 → 開発ブック再Openの順とします。
テストコピーのOpenと開発ブックの再Openでは、通常は自動マクロと起動イベントを抑止します。
起動イベントの検証は、明示した専用テストだけで行います。
明確なテスト失敗は後始末して `ready` に戻します。結果不明なら `isolated` とし、使用中のコピーを無理に削除しません。
コピーはブック外の副作用や未コミット変更の復旧機構にはなりません。

診断・テスト結果は `paths.workspace/logs/` に記録します。
COMの詳細やスタックトレースはログへ出し、API応答には参照先を返します。
未知のダイアログは自動承認せず、タイムアウト時に所有Excelのウィンドウ情報を診断として取得します。

## 承認待ちの安全条件

記録保持とProtected Viewの初期条件はT2で承認済みです。初期契約を正本とします。制御用破棄終了とforceの例外は未承認です。
後続の未承認条件は、該当する処理の実装と故障注入の前に確定します。

| 論点 | 提案 | 確認する影響・確定時期 |
| --- | --- | --- |
| Excelを残す場合の所有記録 | 対象の終了を確認できなければ記録を保持し、追跡情報を消去・上書きしない。終了確認後にクリアする | 初期分は承認済み。初期ライフサイクル契約に従う |
| タイムアウト後の破棄終了 | 通常実行中は終了を拒否するが、`isolated` では保留中COM呼出しがあっても制御用の破棄終了を受け付ける。新しいCOM操作をSTAへ投入せず、所有確認と必要な人の承認の下で終了し、元の呼出しの回収を待つ | R6で採用判断する前に、競合例外とS12の期待動作を確定。初期は手動復旧 |
| Protected Viewの混入 | `ProtectedViewWindows.Count > 0` またはその確認不能時は、自動終了せず `EXCEL_NEEDS_REVIEW` とする | 初期分は承認済み。S11とPoC-1で検証。forceの例外は後続 |

Protected View内のブックは通常の `Workbooks` コレクションに含まれません。
これは[Microsoftの公式説明](https://learn.microsoft.com/en-us/office/vba/api/excel.protectedviewwindow.workbook)で確認した事実です。
したがって `Workbooks` の列挙だけで管理外ブックがないことを確認できるとは扱いません。
上記の拒否条件が実機で意図どおり動くかは、別途検証が必要です。

## 工程ごとに確定する事項

- 基盤の検証とPoC-1の前: 初期に必要な上記の安全条件、手動復旧、6操作の提供範囲と未対応要求の拒否、必要な依存の採用版。MCP SDKはMCP接続前に選定します。
- ライフサイクル処理の実装前: 初期経路は上記のT2契約を使います。起動途中の停止、所有記録の更新失敗、タイムアウト後の遅延完了の扱いは確定済み・未検証です。[確認事項](notes/plan-review.md#未確認の失敗経路)の後続提案は、当該経路への着手時に評価します。
- PoC-2の前: 標準モジュールの反映・マクロ実行・結果取得の契約と、S5・S6の該当部分、S7・S15の結果。ラッパーとJSONの方式は比較結果から決定します。
- R6の各機能の前: クラス・ドキュメントモジュール向けS5・S6、ダイアログ応答、内部テストの契約。
- 自動後始末・同一サーバー内復旧の採用前: 残存Excelへの照会と時間制限、制御用破棄終了・forceの適用範囲、S12の結果。
- テストコピー機能の前: サーバー停止後も管理対象コピーを識別する根拠と、所有記録を更新する時点。
- `project_init` の前: マクロ無効化と初回抽出の成立性。
- 各機能の実装前: [API](api.md)の当該スキーマと、依存する仮説が外れた場合の設計変更。
- 配布前: 配布物の具体的な構成。Windows x64向けの `dotnet publish` を初期案とします。
