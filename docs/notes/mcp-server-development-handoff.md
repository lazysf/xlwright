# MCPサーバー開発フローの標準化に向けた引継ぎ

- Date: 2026-11-01
- 用途: dotfilesリポジトリへ持ち出すための独立した資料。
- 根拠: xlwrightの開発環境整備で確認した実装、実行結果、公式資料。

本書はMCPサーバー自体を開発するための知見をまとめたものです。
dotfiles側での標準化・実装は未実施です。
「確認済み」はxlwrightのWindows環境で確認した範囲を示します。
「標準化候補」は、その経験から他のリポジトリへ展開する際の提案です。

## 開発ループの基本形

標準化候補は、通常のテスト、Inspector CLI、実際のAIクライアントを使い分ける構成です。

| 確認対象 | 主な手段 | 実施の目安 |
| --- | --- | --- |
| 内部ロジック、失敗処理、プロセス制御 | 言語標準のテストや既存チェック | 関係する実装を変更したとき |
| MCP接続、ツール一覧、引数、応答 | Inspector CLI | MCPの公開内容や起動処理を変更したとき |
| 通信の調査、接続を維持した操作 | Inspector GUIまたは接続を維持するテストクライアント | CLIの単発要求では確認できないとき |
| AIによるツール選択、一連の操作、クライアント固有挙動 | 実際のAIクライアント | 利用上の挙動を確認するとき |

通常の反復をAIクライアントの再起動に依存させないことが狙いです。
Inspectorでの成功だけでは、AIクライアントからの利用確認を完了としません。

## Inspectorの導入と実行

### 確認済み

xlwrightではMCPプロジェクトの公式ツールであるInspector 2.13.0を採用しました。
既存のnpm開発依存へ固定版を追加しました。
lockfileによる再インストールも確認しました。
グローバルインストールは使っていません。

CLIでツール一覧と読取り専用の状態照会を実行しました。
GUIでも接続と同じ状態照会を確認しました。
日常の確認にGUIは必須ではありません。

xlwrightの薄い起動スクリプトは、公式Inspectorの`--config`を使います。
単独CLIには公式の引数を渡せます。
この版で使用した引数には、`--cli`、`--server`、`--method tools/list`、`--method tools/call`、`--tool-name`があります。
具体的な対応メソッドと引数は、導入する固定版のヘルプ・公式資料で再確認してください。

### 標準化候補

- 各リポジトリに、通常チェック、Inspector CLI、任意のGUI起動の入口を用意します。
- 既存のパッケージ管理へ組み込みます。Inspectorだけの管理基盤は増やしません。
- 起動スクリプトは作業ディレクトリ、対象成果物、環境変数、ログの配置を補う範囲に留めます。
- JSONの結果と終了コードを利用します。自然言語の出力を解析する独自処理は避けます。

## ビルド成果物と接続中プロセス

### 確認済み

xlwrightは.NET製のstdioサーバーです。
通常のビルド先とは別の場所へ検証用成果物と中間ファイルを出力します。
Inspectorの起動ごとに、その成果物一式をセッション専用ディレクトリへコピーします。
コピー中はビルドと排他します。
GUIがコピーを使用している間も、次のビルドとチェックが成功しました。
ビルドロックの保持中にGUI用コピーを作成しようとすると、起動が拒否されることも確認しました。

実行中GUIは起動時のコピーを使い続けます。
新しい成果物の調査にはInspectorの起動し直しが必要です。
成果物のコピーは、Excelや作業データの隔離にはなりません。

### 標準化候補

接続中の成果物と次回ビルドの出力が競合する場合に、この構成を検討します。
最初にビルドツールの標準機能で出力先を分離できるか確認します。
コピー対象にはDLL本体だけでなく、実行に必要な依存と設定も含めます。
状態照会で起動識別子や成果物ハッシュを返せる場合は、期待したビルドとの一致確認に使います。
言語や実行方式が違うサーバーへ、Windowsのファイル共有や排他の実測をそのまま適用しません。

## ホットリロードを採用する判断

### 確認済み

Hotload MCP 0.3.0では、ダミーサーバーの処理更新、ツール追加、引数変更を確認しました。
同じCodexチャットからの更新も成功しました。
ただし、xlwright本体への適用は採用していません。

評価時のxlwrightには、開始要求への応答後もExcel処理を続けるツールがありました。このツールはADR 0003で削除しました。
ゲートウェイの処理中要求数が0でも、業務処理の完了を意味しません。
評価したHotloadでは、検索や状態照会に伴う設定差分の検出でも再起動が起こり得ます。
本体への適用には、実験開始と更新をまたぐ共通排他などが必要でした。
その追加実装を避け、Inspector中心の反復を選びました。
現在のxlwrightはAIクライアントを登録せず、Inspectorから開発サーバーを起動します。
評価用Hotloadの依存・登録は撤去しました。
アプリ再起動後に、残っていた評価用ゲートウェイの終了も確認しました。

### 標準化候補

同一チャットでの差替えを、すべてのサーバーの前提条件にしません。
必要性は再起動頻度と手動操作の負担で判断します。
採用前には、次の境界をダミーサーバーで確認します。

- 処理中の更新で何を待ち、何を終了するか。
- 応答後も続く処理と、他クライアントからの開始をどう扱うか。
- 結果不明の要求を自動再送しないか。
- 旧プロセスの終了を確認してから新プロセスへ移るか。
- ツールの追加・削除・引数変更が実際のクライアントへ反映されるか。

公式の再読込みAPIの存在だけで、利用中アプリに公開された操作経路や更新完了を確認したとは扱いません。
アプリを再起動した場合も、旧プロセス不在と接続先の同一性を確認します。

## 自己修正ループの検証ゲート

### 確認済み

xlwrightでは次のゲートを統合チェックへ組み込み、一時的な変更で失敗することを確認しました。

- legacyとmodernの両プロトコル世代でのツール一覧と状態照会。
- スキーマの`--strict`検査と、`tools/list`のスナップショットの照合。
- 失敗した工程のログ末尾の出力。
- 実行テストが0件の場合の失敗。

副作用のある経路は、検査だけを実行して戻る入口を別に用意しました。
自動テストはこの入口だけを使うため、検査が壊れても外部アプリへ到達しません。
旧構成では、開始前の検査を持つアダプターを削除した時に、別の起動経路の保護が消えました。

### 標準化候補

- 検査は、起動経路に依存しない最も内側の入口へ置きます。
- 検証したビルドと実行するビルドを、ハッシュで結び付けます。更新時刻の比較は、ファイルの削除を検出しません。
- 設計の根拠は[調査記録](mcp-best-practices.md)を参照してください。

## セッション、失敗、副作用の境界

xlwrightで使用したInspector CLIは、1回の呼出しで接続し、1要求を実行して終了します。
接続に寿命が結び付いた非同期処理の開始と状態照会を、別々のCLI呼出しへ分割しません。
接続を維持するGUIや既存のテストを選びます。

通常チェックには、実Excelの起動や実データの更新を含めていません。
ツール一覧と読取り専用の状態照会をInspectorの自動チェックに使いました。
結果不明の副作用は、自動再送やガード削除で解消しません。
対象の状態と証拠を確認してから、復旧の判断を行います。

統合チェックは最初の失敗で後続工程を止めます。
工程別の標準出力・標準エラーと、構造化した成否をローカルへ保存します。
子プロセスを起動できない失敗も、失敗工程として記録することを確認しました。
これは他のリポジトリでも標準化する候補です。

## ローカル環境で踏んだ問題

| 問題 | 確認結果と扱い |
| --- | --- |
| Inspector起動中の依存再インストール | Windowsでは使用中のネイティブモジュールの削除が拒否されました。GUIでサーバーを切断し、Inspectorを終了してから再インストールしました |
| sandboxとユーザー環境の相違 | sandboxでのNode指定版不在に対し、通常ユーザー環境ではNodeとnpmが使えました。実行経路の差を、未インストールと誤認しません |
| シェルの版 | 通常チェックはWindows PowerShell 5.1で確認しました。別のシェルでの成功を代用しません |
| 設定削除後のプロセス残存 | MCP登録を削除しても、アプリに読み込み済みのゲートウェイは残りました。再起動後にプロセス終了を照合しました |
| ログ設定の思い込み | 採用版の実装を確認し、`MCP_LOG_FILE`による実ファイル生成まで検証しました。設定名を置いただけでは有効としません |

xlwrightではGUIを127.0.0.1へbindしました。
認証なしのAPI要求が401になることを確認しました。
secret storeはmemoryを使い、状態・ログの出力先はセッションごとに設定しました。
起動URLやログにはローカル情報が含まれ得るため、共有前に内容を確認します。
これらの設定名と効果は、別版への更新時に再確認が必要です。

## コンテキスト・利用枠・実行時間

以下は利用者の要望に基づく運用候補です。
5時間枠・週枠の消費削減率や実行時間の短縮率は測定していません。

- 既存の仕組み、確認済みの資料、直近の検証結果を先に使います。
- 調査範囲と検証範囲を変更内容に合わせます。文書だけの変更で.NET全体を再ビルドしません。
- 統合チェックが通過した後は、新しい変更や未解決の懸念がある部分だけ再確認します。
- チャットには成否、失敗工程、証拠の場所を返します。成功した大量ログはローカルへ残します。
- CLIで定型確認を実行します。GUIは画面や接続継続が必要な調査に使います。
- 引継ぎには確定した方針、確認結果、未確認事項、次の操作を残します。再探索を減らします。
- 副作用、終了、復旧に必要な検証は、利用枠の節約を理由に省略しません。

## dotfilesと各リポジトリの分担候補

| dotfilesで管理する候補 | 各リポジトリへ残すもの |
| --- | --- |
| 開発ループの共通指針、ツール選択の判断基準 | ビルドとテストの具体的なコマンド |
| CLI優先、ログと引継ぎの方針 | ツール名、スキーマ、成果物の構成 |
| 再読込みを評価する観点 | 起動設定、作業ディレクトリ、依存の固定版 |
| 失敗・結果不明・副作用を扱う原則 | 実データ、外部アプリ、所有記録、復旧の固有条件 |

dotfiles側では、まず共通指針と導入時の確認項目を整理するのが候補です。
汎用ランチャーや全言語共通のビルド基盤が必要かは、複数リポジトリでの重複を確認してから判断します。
本書だけを根拠に、グローバル依存、認証設定、既存MCP登録を一括変更しません。
